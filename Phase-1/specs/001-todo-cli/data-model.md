# Data Model: Todo CLI Application

**Feature**: 001-todo-cli
**Date**: 2026-01-01
**Phase**: 1 - Design

## Overview

This document defines the data model for the Todo CLI application. The model is intentionally simple, consisting of a single entity (Task) with clear validation rules and state transitions.

## Entities

### Task

Represents a single todo item with title, description, and completion status.

**Attributes**:

| Attribute   | Type   | Required | Default     | Constraints                          | Description                                    |
|-------------|--------|----------|-------------|--------------------------------------|------------------------------------------------|
| id          | int    | Yes      | Auto        | > 0, unique, sequential              | Unique identifier for the task                 |
| title       | str    | Yes      | -           | 1-500 chars, non-empty after strip   | Short description of the task                  |
| description | str    | No       | ""          | 0-2000 chars                         | Optional detailed information                  |
| completed   | bool   | Yes      | False       | True or False                        | Completion status (True = done, False = todo) |

**Validation Rules**:

1. **ID Validation**:
   - Must be positive integer (> 0)
   - Auto-generated by TaskService, users cannot specify
   - Sequential (1, 2, 3, ...)
   - Never reused after deletion

2. **Title Validation**:
   - Cannot be None or empty string
   - Must have at least 1 non-whitespace character after strip()
   - Maximum 500 characters
   - Raise ValueError if validation fails: "Title cannot be empty"

3. **Description Validation**:
   - Optional (empty string is valid)
   - Maximum 2000 characters
   - No minimum length requirement

4. **Completed Validation**:
   - Must be boolean (True or False)
   - Defaults to False for new tasks
   - Can be toggled any number of times

**Invariants**:

- A Task with a valid ID always exists in the TaskService until explicitly deleted
- Task IDs are immutable once assigned
- Title and description can be updated, but never set to invalid values
- Completed status can be toggled freely

---

### TaskService (Storage & Business Logic)

Manages in-memory storage and operations on tasks.

**State**:

| Attribute  | Type            | Description                                      |
|------------|-----------------|--------------------------------------------------|
| _tasks     | dict[int, Task] | In-memory storage: task ID → Task object         |
| _next_id   | int             | Counter for ID generation (starts at 1, increments only) |

**Invariants**:

- `_next_id` is always greater than any existing task ID
- `_next_id` never decrements (even after deletions)
- Task IDs in `_tasks` are always < `_next_id`
- All tasks in `_tasks` have valid data (passed validation)

## State Transitions

### Task Lifecycle

```
[Create] → INCOMPLETE (completed=False)
           ↓
           ↓ [Mark Complete]
           ↓
           COMPLETE (completed=True)
           ↓
           ↓ [Mark Incomplete]
           ↓
           INCOMPLETE (completed=False)
           ↓
           ↓ [Delete]
           ↓
           [Removed from storage]
```

**Transitions**:

1. **Create**: `add(title, description)` → Task with ID=_next_id, completed=False
2. **Mark Complete**: `complete(id)` → Set task.completed=True
3. **Mark Incomplete**: `uncomplete(id)` → Set task.completed=False
4. **Update**: `update(id, title?, description?)` → Modify title/description, completed unchanged
5. **Delete**: `delete(id)` → Remove from _tasks, _next_id unchanged

**Notes**:
- Tasks can transition between INCOMPLETE ↔ COMPLETE multiple times
- Update operation does not change completion status
- Delete is irreversible (no undo functionality)

## Validation Error Scenarios

| Operation        | Invalid Input                  | Error Message                                  |
|------------------|--------------------------------|------------------------------------------------|
| add              | Empty title                    | "Title cannot be empty"                        |
| add              | Title > 500 chars              | "Title must be 500 characters or less"         |
| add              | Description > 2000 chars       | "Description must be 2000 characters or less"  |
| update           | Non-existent ID                | "Task not found"                               |
| update           | Empty title (if provided)      | "Title cannot be empty"                        |
| update           | Title > 500 chars              | "Title must be 500 characters or less"         |
| delete           | Non-existent ID                | "Task not found"                               |
| complete         | Non-existent ID                | "Task not found"                               |
| uncomplete       | Non-existent ID                | "Task not found"                               |
| get              | Non-existent ID                | "Task not found"                               |
| Any operation    | Invalid ID type (not int)      | "Invalid task ID"                              |
| Any operation    | ID ≤ 0                         | "Invalid task ID"                              |

## Data Access Patterns

### Read Operations

1. **Get All Tasks**: O(n) - Iterate over all values in _tasks dictionary
   - Returns list of tasks sorted by ID (ascending)
   - Returns empty list if no tasks exist

2. **Get Single Task**: O(1) - Dictionary lookup by ID
   - Returns Task object if exists
   - Raises TaskNotFoundError if not exists

### Write Operations

1. **Add Task**: O(1)
   - Create Task object with validation
   - Assign ID = _next_id
   - Store in _tasks[id]
   - Increment _next_id
   - Return created Task

2. **Update Task**: O(1)
   - Lookup task by ID
   - Validate new title/description (if provided)
   - Update task fields
   - Return updated Task

3. **Delete Task**: O(1)
   - Check if ID exists
   - Remove from _tasks
   - _next_id unchanged (IDs never reused)

4. **Toggle Complete Status**: O(1)
   - Lookup task by ID
   - Toggle completed field
   - Return updated Task

## Memory Considerations

**In-Memory Storage**:
- No persistence to disk/database
- All data lost when application exits
- Constitution requirement: explicit in-memory only

**Memory Usage Estimation**:
```
Per Task Object:
- ID: 28 bytes (Python int)
- Title: ~50-500 bytes (average ~100 bytes)
- Description: ~0-2000 bytes (average ~200 bytes)
- Completed: 28 bytes (Python bool)
Total per task: ~356 bytes average

For 1000 tasks: ~356 KB
For 10000 tasks: ~3.56 MB
```

**Performance**:
- Target: < 1 second for all operations with 1000 tasks
- Expected: Microseconds per operation (dictionary operations are O(1))
- Bottleneck: List/display operations (O(n) for sorting)

## Implementation Notes

### Dataclass Definition

```python
from dataclasses import dataclass

@dataclass
class Task:
    """Represents a single todo task."""

    id: int
    title: str
    description: str = ""
    completed: bool = False

    def __post_init__(self) -> None:
        """Validate task fields after initialization."""
        if not isinstance(self.id, int) or self.id <= 0:
            raise ValueError("Invalid task ID")

        if not self.title or not self.title.strip():
            raise ValueError("Title cannot be empty")

        if len(self.title) > 500:
            raise ValueError("Title must be 500 characters or less")

        if len(self.description) > 2000:
            raise ValueError("Description must be 2000 characters or less")
```

## Relationships

This is a single-entity model with no relationships. Each Task is independent.

**No Relationships**:
- No task dependencies (tasks don't reference other tasks)
- No categories or tags
- No user ownership (single-user app)
- No task history or audit trail

**Future Considerations** (Out of Scope for Phase 1):
- Task categories/tags
- Due dates
- Priority levels
- Task dependencies
- Recurring tasks

---

## Summary

The data model is intentionally minimal to satisfy the constitution's "Simplicity First" principle:

- **1 Entity**: Task
- **4 Attributes**: id, title, description, completed
- **5 Operations**: add, list, update, delete, toggle complete
- **0 Relationships**: No complex associations
- **In-Memory Only**: No persistence complexity

This design supports all functional requirements from the specification while maintaining extreme simplicity.
